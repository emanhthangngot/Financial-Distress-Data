# 01 Data Generator - Stage 1 As-Built Contract

## Objective

Stage 1 uses deterministic source adapters to exercise the same data contracts that later live Vietnamese market collectors must satisfy. Fast contract tests retain `VnstockFixtureAdapter`; rubric-scale problem simulation uses the typed configurable generator documented in [Configurable Problem Generator](data-generator.md). The repository does not call live HOSE, HNX, SSI, or `vnstock` endpoints during tests or evidence runs.

This document describes the current implemented contract, not a Phase 2 or cloud roadmap.

## Scope

In scope:

- batch company master rows
- batch quarterly financial statement rows
- batch daily market price rows
- Kafka-style price, news, and market alert events
- deterministic distress label generation from financial statement rows
- local runtime evidence generated by Airflow, MinIO, PostgreSQL, Spark-compatible jobs, and DuckDB

Out of scope:

- live-source scraping or paid API integration
- Phase 2 drift simulation
- ML training, scoring, feature store serving, or model registry
- AWS S3, Glue, Athena, RDS, EMR, MSK, SageMaker, Kubernetes

## Timestamp Conventions

- `event_timestamp`: when the source business event happened.
- `created_ts`: when the source or normalized local record was created.
- `ingest_ts`: when the row entered the local Bronze layer during evidence materialization.
- `report_release_date`: when a financial statement became visible for point-in-time joins.

Acceptance criteria:

```text
Collector fixture adapter -> emits batch rows -> every row has created_ts and source_system.
Bronze materialization job -> writes runtime rows -> adds ingest_ts without replacing event_timestamp or created_ts.
Bronze-to-Silver transform -> receives duplicate business keys -> keeps the row with the latest created_ts.
Feature/OBT builder -> joins market features to a report row -> excludes feature events after the reference event timestamp.
```

## Batch Dataset Contracts

The authoritative schema contracts live in `src/metadata/schema_registry.py` and are seeded into `project_metadata.schema_version_registry` by `sql/init_project_metadata.sql`.

### companies

Grain: one row per company snapshot.

Business key: `ticker`.

Required columns:

```text
ticker
company_name
exchange
created_ts
```

Nullable contract columns:

```text
industry
sector
listing_date
delisted_flag
company_size
```

Runtime fixture rows also include `source_system = vnstock_fixture`.

### financial_statements

Grain: one row per ticker per report period.

Business key: `ticker`, `report_period`.

Required columns:

```text
ticker
report_period
fiscal_year
fiscal_quarter
total_assets
total_liabilities
equity
created_ts
```

Nullable contract columns:

```text
current_assets
current_liabilities
revenue
ebit
interest_expense
net_income
operating_cash_flow
retained_earnings
statement_type
report_release_date
event_timestamp
```

Runtime fixture rows include `source_system = vnstock_fixture`. `statement_type` is nullable because the fixture and some future local sources may not distinguish consolidated and standalone statements.

### market_prices_daily

Grain: one row per ticker per trading date.

Business key: `ticker`, `trading_date`.

Required columns:

```text
ticker
trading_date
close_price
volume
created_ts
```

Nullable contract columns:

```text
open_price
high_price
low_price
market_cap
shares_outstanding
event_timestamp
```

Runtime fixture rows include `source_system = vnstock_fixture`. Stage 1 uses raw close prices. Split-adjusted or dividend-adjusted series are not implemented until a source supplies adjustment factors or an explicit adjustment flag.

## Streaming Dataset Contract

Kafka topics:

```text
financial.price_events
financial.news_events
financial.alert_events
```

The registry entry `stream_events` requires:

```text
event_id
event_type
ticker
event_timestamp
created_ts
```

Nullable registry fields:

```text
source_sequence
raw_payload_hash
```

Implemented event types:

| Event type | Topic | Payload fields |
|---|---|---|
| `price_update` | `financial.price_events` | `price`, `volume` |
| `news_sentiment` | `financial.news_events` | `sentiment_score`, `risk_keyword_flag`, `severity_score`, `source_url` |
| `market_alert` | `financial.alert_events` | `alert_type` |

`price_update` and `news_sentiment` event IDs are deterministic hashes of the event payload. `market_alert` currently uses a UUID.

The micro-batch consumer flushes when either condition is met:

```text
record_count >= 1000
elapsed_seconds >= 60
```

Streaming Bronze path:

```text
s3a://financial-distress-lake/bronze/kafka/{topic}/event_date=YYYY-MM-DD/event_hour=HH/batch_id={uuid}/
```

The real local E2E DAG produces fixture stream events to Kafka, consumes them back, and writes Bronze Parquet before the Spark lakehouse job builds Gold news and alert facts.

## Distress Labels

`distress_labels` is derived locally by `src/transforms/compute_distress_labels.py` from financial statement rows. It is not a ground-truth bankruptcy label.

Grain: one row per ticker per report period.

Columns:

```text
ticker
report_period
event_timestamp
created_ts
distress_label
distress_reason
z_score
label_source
label_confidence
training_eligible
rule_version
```

Constants:

```text
rule_version = v1
label_source = rule_based_v1
zero_liabilities_x4_cap = 99.0
```

Altman Z double-prime:

```text
Z'' =
  6.56 * (working_capital / total_assets)
+ 3.26 * (retained_earnings / total_assets)
+ 6.72 * (ebit / total_assets)
+ 1.05 * (equity / total_liabilities)
```

Warning rules:

- `debt_to_asset > 0.8`
- `current_ratio < 1.0`
- `net_income < 0` for two immediately consecutive quarters
- `equity < 0`
- `ebit_interest_coverage < 1.0`

Financial-sector exclusion:

- Sectors or industries matching banks, insurance, securities, brokerage, diversified financials, financial services, or GICS sector code `40` are excluded from Altman Z'' labeling.
- Excluded rows return `distress_label = NULL`, `distress_reason = financial_sector_excluded`, `label_confidence = NULL`, and `training_eligible = false`.
- The local config file `configs/sector_exclusion.yaml` documents the exclusion policy.

Label policy:

- `distress_label = 1` when `z_score < 1.1` or at least two warning rules are true.
- `distress_label = 0` when `z_score > 2.6` and fewer than two warning rules are true.
- If `z_score` is null and fewer than two warning rules are true, `distress_label = NULL` and `distress_reason` includes `insufficient_data`.
- If `1.1 <= z_score <= 2.6` and fewer than two warning rules are true, `distress_label = 0`, `distress_reason` includes `gray_zone_monitor`, `label_confidence = low`, and `training_eligible = false`.

## Runtime Modes

### Fast Contract Mode

Used by PyTest and lightweight evidence helpers.

```text
VnstockFixtureAdapter
  -> collectors
  -> in-memory Bronze rows with ingest_ts
  -> Python Bronze-to-Silver helpers
  -> Python Gold builders
  -> evidence JSON files under docs/evidence/
```

### Real Local E2E Mode

Implemented by `dags/stage1_real_e2e_pipeline.py`.

```text
materialize_bronze_batch_objects
  -> produce_fixture_stream_events_to_kafka
  -> consume_kafka_events_to_bronze
  -> run_spark_bronze_to_silver_gold
  -> run_silver_gold_dq_gate
  -> write_project_metadata_rows
  -> run_duckdb_validation_and_publish_evidence
```

This mode writes Bronze/Silver/Gold Parquet to MinIO, persists metadata and DQ rows to local PostgreSQL, validates Gold objects through DuckDB, and publishes evidence artifacts under `evidence/stage1/run_id=...` in MinIO.

## Volume Strategy

The committed adapter fixtures remain intentionally small. The configurable generator adds separate CI and evidence profiles; the verified evidence profile contains 10,000 base companies, 80,000 financial statements, 10,000 market prices, and 50,000 stream events.

The previous `>=20M` record target is an optional replay/load-testing target for later source-access work. It is not an implemented Stage 1 guarantee.

Acceptance criteria:

```text
CI test suite -> runs fixture collectors -> produces deterministic row counts without network access.
Real E2E DAG -> runs against local services -> produces Bronze batch rows and Kafka Bronze stream batches in MinIO.
Maintainer -> inspects generated evidence -> can trace counts from Bronze inputs through Silver and Gold outputs.
```
